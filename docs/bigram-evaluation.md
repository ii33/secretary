# 中文检索方案实测：bigram、trigram 与 embedding

> 目的：给秘书记忆库选中文检索方案。对比 `unicode61` 原生、bigram 预处理、`trigram`、以及 embedding（bge-small-zh-v1.5）+ 混合检索。
> 语料：dots 对话导出 1,888 条非空消息（用户 602 / 助手 1,286），212,202 字；取 1,281 条 ≥20 字的助手消息作为文档，187k 字。
> 环境：Python 3.12 + SQLite 3.54（FTS5）+ fastembed/onnxruntime CPU，本机 Windows；时间只代表本机量级。
>
> **复现口径**
> - 存储数字（raw 1.38MB / bigram 1.74MB / trigram 3.30MB）是 **contentless FTS**，用 [scripts/bench_memory_contentless.py](secretary-office/scripts/bench_memory_contentless.py) 复现；`bench_memory.py` 建的是普通 FTS（含 docs 字段），所以尺寸更大。
> - 1.3k 文档的查询延迟来自 `bench_memory.py`（普通 FTS）；20k 查询数字是**重复语料合成的量级测试**，未保留 20k 库，属于外推结果，不是最终语料。
> - embedding 数字来自 `bench_embed.py` / `bench_embed_eval.py`（fastembed + bge-small-zh-v1.5，需联网下载约 90MB 模型；缓存未随附）。
> - 所有数字只代表本机 CPU、单进程、特定语料；换机器/换语料要重跑。

---

## 0. 结论先行

1. **中文必须做 bigram 或 trigram，原生 `unicode61` 不可用。** 它把一整段连续中文当成一个 token；搜“膜系”命中不了“膜系优化算法”。
2. **bigram 综合最优。** 2–8 字精确短语召回 100%，自然问句 recall@5 78%，2 字查询 100%；原生只有 27%/3%。
3. **trigram 是次选。** 3 字以上精确短语 100%，但 2 字查询 0%，自然问句 recall@5 62%，存储是 bigram 的 1.9 倍。只适合“只搜长短语”的场景。
4. **成本很低。** 1,281 条文档 / 187k 字：bigram 内容less索引 1.74MB（约 1.36KB/条、9.3 字节/字），构建 2.4 秒，单条增量写入约 1.5ms；1.3k 文档查询 p50 约 6ms，20k 文档 p50 约 32ms。
5. **先上 bigram，不上 embedding。** 语义近义词（“报表/周报”“上下文/token”）是 bigram 的短板，先用档案室做查询改写；等真实评测显示召回不够，再加向量。embedding 的补充实测见第 7 节：**单用不如 bigram，混合用只在语义题上略有增益，第一版不值得引入。**

## 1. 实测结果

### 1.1 精确短语召回（已知条目，n=30/长度）

从文档中随机取 2/3/4/5/6/8 字连续中文短语（全语料出现 ≤3 次），搜索该短语，看原文档是否在 top-5。

| 查询长度 | raw（unicode61） | bigram | trigram |
|---|---|---|---|
| 2 字 | 1/30 | **30/30** | 0/30（trigram 需要 ≥3 字） |
| 3 字 | 0/30 | **30/30** | 30/30 |
| 4 字 | 0/30 | **30/30** | 30/30 |
| 5 字 | 0/30 | **30/30** | 30/30 |
| 6 字 | 3/30 | **30/30** | 30/30 |
| 8 字 | 0/30 | **30/30** | 30/30 |

top-1 命中率（bigram）：2 字 22/30、3 字 25/30、4 字 26/30、5 字 29/30、6 字 29/30、8 字 30/30。

**解读**：bigram 的精确召回接近完美；trigram 在 2 字查询上直接失效；raw 基本不可用。

### 1.2 自然问句召回（用户消息 → 同轮助手回复，n=60）

查询 = 用户原话（6–80 字），文档 = 助手消息；看同轮助手回复是否在 top-5。

| 方案 | top-1 命中 | recall@5 | 查询 p50 | p95 |
|---|---|---|---|---|
| raw unicode61 | 8/60（13%） | 16/60（27%） | 2.0ms | 3.9ms |
| **bigram** | **32/60（53%）** | **47/60（78%）** | 6.0ms | 10.1ms |
| trigram | 19/60（32%） | 37/60（62%） | 3.0ms | 6.1ms |

**解读**：
- 自然问句比精确短语难，因为用户说“改一下窗口列表”，助手回复可能说“下拉列表改为两级”，词面不完全重合。
- bigram 明显领先；但 top-1 只有 53%，说明**排序还需要覆盖度、时间、重要度、类型权重和查询改写**，不能只靠 BM25。
- 这个测试只索引助手消息；生产上按“turn（用户+助手+brief/report）”建索引，召回会更高，因为用户原话也在同一 turn 文档里。

### 1.3 2 字查询

中文里大量关键词是 2 字（“膜系”“优化”“窗口”“材料”），这是 trigram 的硬伤：

| 方案 | recall@5 | 说明 |
|---|---|---|
| bigram | 30/30 | 2 字就是一个 bigram token |
| trigram | 0/30 | trigram 需要 ≥3 字符 |
| raw | 1/30 | 除非整段中文恰好只有这 2 字 |

**结论：如果只用 trigram，必须额外为 1–2 字查询做 LIKE 回退；bigram 不需要。**

## 2. 成本

### 2.1 存储（内容less FTS，rowid 映射）

| 方案 | DB 大小 | 相对文本 | 每条文档 |
|---|---|---|---|
| raw unicode61 | 1.38 MB | 2.5× | 1.07 KB |
| **bigram** | **1.74 MB** | **3.1×** | **1.36 KB** |
| trigram | 3.30 MB | 5.9× | 2.57 KB |

- bigram 比 raw 多 **26%**，但比 trigram 少 **47%**。
- 内容less 模式（`content=''`，只存索引，不存 tokenized 正文）比普通 FTS 省约 **34%**。
- 原文字段仍存在 `turn/message` 表，约 3 字节/字；检索命中后按 id 回表取原文，做高亮。
- 粗估：20k 条 turn ≈ **26MB**；100k 条 ≈ **130MB**。个人项目一年通常远低于 20k 条 ES 记忆，完全可接受。

### 2.2 构建与写入

| 指标 | 数值 |
|---|---|
| 全量构建 1,281 条 / 187k 字 | raw 0.22s，bigram 2.4s，trigram 0.6s |
| bigram 单条构建成本 | 约 1.9ms |
| 增量写入（WAL + `synchronous=NORMAL`，每条 commit） | p50 约 1.6ms |
| 批量（200 条一个事务） | 约 1.2ms/条 |

早期用默认 rollback journal 时，每条 commit 高达 ~190ms；**必须用 WAL + NORMAL，并按 turn/批次提交**。写入成本不是问题，commit 策略才是。

### 2.3 查询延迟

| 场景 | p50 | p95 |
|---|---|---|
| 1,281 条，精确短语 | 1.8ms | 2.4ms |
| 1,281 条，自然问句 | 6.0ms | 10.1ms |
| 20,000 条，自然问句（60 个 bigram 全 OR） | 32ms | 70ms |
| 20,000 条，限制 8 个稀有 bigram | 23ms | 40ms |

- 20k 条文档是“重复语料放大”的合成测试，存储偏乐观；查询量级仍有参考价值。
- 对个人记忆库，**p95 < 100ms 完全可用**；如果以后到 100k 条，建议限制查询词数 + 定期 optimize。
- 查询慢的主因是 OR 词太多且常见 bigram 太多；限制到 12–20 个稀有 bigram 可明显降延迟。

## 3. 为什么 bigram 有效，以及它的边界

### 3.1 有效的原因

- 中文没有空格，bigram 把“膜系优化”拆成“膜系/系优/优化”，任意 2 字词都能命中；
- 精确短语查询 `"膜系 系优 优化"` 是连续 token 短语，等价于子串匹配；
- 自然问句用 OR + BM25，能覆盖用户和助手的不同措辞；
- 不需要词典、分词器、嵌入模型，完全离线、可重建。

### 3.2 边界

| 问题 | 表现 | 缓解 |
|---|---|---|
| 语义近义 | “报表”搜不到“周报”，“上下文”搜不到“token” | 档案室查询改写；后期 embedding |
| 1 字查询 | bigram 没有单字 token | LIKE 回退；或额外建 char 索引 |
| 常见 bigram 噪声 | “我们”“可以”“这个”导致误命中 | 停用词表 + 稀有词覆盖度 + BM25 + 重排 |
| 长查询 | OR 词多、延迟上升 | 取 12–20 个最稀有 bigram；先 AND 后 OR 回退 |
| 繁简/错别字 | 不匹配 | 统一转简体；后期模糊/向量 |
| 英文混合 | 单词按小写 token，正常 | 保持 |
| 排序 | top-1 只有 53% | 覆盖度 + 时间衰减 + 重要度 + 类型权重 + 档案室综合 |

## 4. 建议的实现参数

### 4.1 索引

```sql
-- 内容less：只存索引，不存 tokenized 正文
CREATE VIRTUAL TABLE turn_fts USING fts5(
  body,
  content='',
  tokenize='unicode61'
);
```

- 写入时 `body = bigram_tokenize(turn_text)`；
- `rowid` = `turn.id`（整数主键），检索后回表 `turn` 取原文；
- turn 文本 = 用户消息 + 秘书回复 + brief + report 摘要；
- notes/decisions 单独建 `note_fts`，不要和 turn 混；
- 定期 `INSERT INTO turn_fts(turn_fts) VALUES('optimize')`。

### 4.2 查询

1. 归一化：全角转半角、英文小写、去首尾空白。
2. 抽取：中文 bigram + 英文单词；去掉单字、纯标点。
3. 取最稀有的 12–20 个 bigram（按全局 df）；OR 成 FTS5 查询。
4. 取 top 30–50；按以下重排：
   - 稀有 bigram 覆盖度（命中数/查询稀有词数）；
   - 精确短语加成（用户加引号时）；
   - 时间衰减（越近越高）；
   - 重要度（决策/偏好/artifact > 普通对话）；
   - 类型权重（note/decision > report > turn）。
5. 无结果或 1 字查询：`LIKE '%q%'` 回退，limit 5。
6. 输出：`{id, date, kind, snippet(≤160字), score}`；snippet 由原文按命中位置截取并高亮。

### 4.3 写入

- `journal_mode=WAL`，`synchronous=NORMAL`；
- 按 turn 或每 10–20 条消息一个事务；
- 幂等键 `(session_id, seq)`；
- 写入与索引在同一事务；
- 崩溃后从日志回填。

### 4.4 评测（上线前必做）

用真实 ES 对话建 30–50 个问题，覆盖：

- 精确事实：“上次用的提交号是多少？”
- 决策：“为什么决定不先上 AI 模型？”
- 偏好：“报告用什么格式？”
- 多跳：“A 和 B 两次改动之间发生了什么？”
- 时间：“上周三做到哪？”
- 同义/口语：“那个膜系优化的事后来咋样了？”

指标：recall@5、top-1 命中、引用正确率、p95 延迟、上下文占用。**dot 语料只是代理，真实 ES 记忆线更短、更偏项目术语，必须用自己的数据复测。**

## 5. 和 embedding 的比较

| 维度 | bigram FTS | embedding RAG |
|---|---|---|
| 精确词/数字/提交号 | 强 | 弱（向量不擅精确匹配） |
| 同义/口语/跨语言 | 弱 | 强 |
| 成本 | 几乎为零 | 每次查询一次 embedding + 存储向量 |
| 可解释性 | 高（命中词可高亮） | 中 |
| 离线 | 完全离线 | 依赖模型/API |
| 维护 | 低 | 中（模型版本、维度、重嵌） |

**建议：bigram 做第一层；档案室做查询改写做第二层；embedding 只在真实评测显示语义召回不足时再加，做混合检索（BM25 + 向量 + RRF）。** 具体实测见下一节。

---

## 6. 最终建议

- **采用 bigram + 内容less FTS5**，索引单位用 turn，不用 message。
- 查询限制 12–20 个稀有 bigram，top 30–50 重排，1 字走 LIKE 回退。
- WAL + NORMAL，按 turn/批次提交。
- 先不做 embedding、不引入 jieba；保持零依赖、可重建。
- 上线前用真实 ES 对话做 30–50 题评测；如果 top-1 仍低于 60%，优先加“档案室查询改写/重排”，而不是直接上向量。
- 预算：20k 条 turn 约 26MB、构建约 40 秒、查询 p95 约 70ms、增量写入约 1.5ms/条。对个人项目完全够用。

## 7. embedding 补充实测（bge-small-zh-v1.5）

> 模型：`BAAI/bge-small-zh-v1.5`（512 维，约 90MB，ONNX CPU）；查询加 BGE 中文检索前缀（“为这个句子生成表示以用于检索相关文章：”）。
> 文档：同一批 1,281 条助手消息；向量做 L2 归一化；余弦相似度。
> 注意：这是小模型 + CPU + dots 语料，不代表更强模型/API 的上限。

### 7.1 成本

| 项 | 数值 |
|---|---|
| 模型文件 | 约 90MB（不含 onnxruntime） |
| 向量存储 | 512 × float32 = 2KB/条；1,281 条 2.6MB；20k 条约 41MB（int8 约 10MB） |
| 全量构建（1,281 条 / 185k 字） | 174 秒，约 136ms/条；20k 条 naive 约 45 分钟 |
| 查询（embed + 余弦，1.3k 条） | 5.8ms（无前缀）/ 13.5ms（带前缀） |
| 20k 条查询 | 余弦额外约 5–10ms，预计 15–25ms |
| Node/DSH 集成 | 需要 Python sidecar（fastembed/onnxruntime）或 onnxruntime-node + tokenizer；多一个常驻进程/模型文件 |

### 7.2 效果

**自然问句（用户原话 → 同轮助手回复，n=60）**

| 方案 | top-1 | recall@5 |
|---|---|---|
| bigram BM25 | 32/60（53%） | 47/60（78%） |
| embedding | 36/60（60%） | 45/60（75%） |
| hybrid（BM25 + 向量 RRF） | **38/60（63%）** | 47/60（78%） |

**精确短语（已知条目，5 字，n=30）**

| 方案 | top-1 | recall@5 |
|---|---|---|
| bigram BM25 | 29/30 | 30/30 |
| embedding | 7/30 | 10/30 |
| hybrid | 29/30 | 30/30 |

**语义改写（18 题，关键词目标）**

| 方案 | top-1 | recall@5 |
|---|---|---|
| bigram BM25 | 5/18 | 6/18 |
| embedding | 1/18 | 8/18 |
| embedding + 前缀 | 6/18 | 8/18 |
| hybrid | 4/18 | 7/18 |

**但这个“关键词目标”指标不可靠。** 人工抽查 10 题发现：

- 对“显卡参与光学计算”“图形界面测试进程崩溃”“镀膜设计先用物理初始结构”“聊天入口按钮又出现了”这类语义改写，embedding top-1 明显比 BM25 更相关；BM25 经常抓到字面相近但主题偏掉的文档。
- 对“token 统计字段缺失”“数据库连接没关导致文件占用”这类精确词，两者打平；但换成提交号、测试数、文件路径，BM25 会明显更稳（known-item 30/30 vs 10/30）。
- 语义改写题的“唯一关键词目标”不是唯一相关文档，所以 embedding 的 top-1 常常是另一篇同样相关的文档，被指标误判为失败。

### 7.3 解读

1. **embedding 不能替代 bigram。** 精确词、数字、提交号、文件路径是项目记忆的高频查询；embedding 在这些题上明显吃亏。
2. **embedding 确实补语义。** 人工抽查里 4/10 题 embedding 明显更相关；但自然问句整体只提升 top-1 4–6 个百分点，recall@5 没提升。
3. **hybrid 是唯一合理形态。** 保留 BM25 的精确命中，再用向量补语义；known-item 仍是 30/30，自然问句 top-1 从 53% 到 63%。
4. **成本不在存储，在构建和集成。** 20k 条向量只有 41MB；但全量构建 45 分钟（可优化）、模型 90MB、Node 侧要 sidecar/ONNX，才是引入 embedding 的真实代价。
5. **档案室查询改写可能更划算。** 让档案室把“报表”改写成“周报/报告/文档”，再走 bigram，能覆盖相当一部分语义缺口，且零模型、零向量、可解释。

### 7.4 建议

- **M1/M2 不引入 embedding。** 先用 bigram + 档案室查询改写；这是当前性价比最高的组合。
- 只有当真实 ES 评测显示**语义类问题失败率 >10%**（同义、口语、跨词表述），才加 hybrid；不要替换 bigram，只叠加。
- 加的话：
  - 先试 API embedding（无本地模型/sidecar，代价是网络与隐私）；
  - 本地模型优先选比 bge-small 更强的中文/多语模型，但先测收益是否值得 90MB+ 和构建时间；
  - 向量按 **turn** 存，int8/float16；后台批量回填，不阻塞启动；
  - 检索用 RRF 融合 BM25 top30 + 向量 top30；精确词查询仍走 BM25 优先。
- 如果只能选一个：**bigram。** 这规模下，它覆盖 80% 的查询，成本几乎为零；embedding 是锦上添花，不是地基。
